# isucon14 計測と改善ログ

推測でコードをいじる前に、どこが遅いかを数字で特定するための環境と、その記録。

このドキュメント内のパスは `FStudent/` を基準にした相対パスで書いている。
`isucon14/` 配下の設定ファイルは変更せず、計測に必要な設定はすべて実行時に外から与えている。

## 1. 計測ツールの導入

```bash
brew install alp percona-toolkit
```

| ツール | 役割 |
| --- | --- |
| `pt-query-digest` | MySQL のスロークエリログを集計し、重いクエリを順位付けする |
| `alp` | nginx のアクセスログを集計し、重いエンドポイントを順位付けする |

ISUCON の定番ツールで、本番環境でも同じものを使う。

## 2. 仕組み

計測のために 2 つの仕掛けを入れている。どちらも `isucon14/` の外で完結している。

**MySQL のスロークエリログ** は `SET GLOBAL` だけで有効化している。設定ファイルを置き換えていないので、コンテナを作り直せば元の状態に戻る。`long_query_time = 0` にして全クエリを記録する。

**nginx のアクセスログ** は `static-proxy/nginx.conf` で JSON 形式に出力し、`static-proxy/compose.yml` のボリューム経由で `measure/logs/` に書き出している。コンテナを停止してもログは残る。

## 3. 使い方

計測付きで走行し、両方のレポートを出す。

```bash
cd measure
DURATION=60 ./run-measure.sh
```

個別に操作したい場合。

```bash
./mysql-slowlog.sh on      # 全クエリの記録を開始(走行前)
./mysql-slowlog.sh off     # 記録を停止
./mysql-slowlog.sh report  # 集計して表示
./mysql-slowlog.sh status  # 現在の設定を確認

./nginx-alp.sh reset       # アクセスログを空にする(走行前)
./nginx-alp.sh report      # 集計して表示
```

レポートは `measure/logs/` に `slow-digest.txt` と `alp.txt` として残る。このフォルダは `.gitignore` で除外してある。

### 重要: 計測走行とスコア走行は分ける

`run-measure.sh` は全クエリをディスクに書くため、その負荷でアプリが遅くなる。**ここで出るスコアは改善の前後比較に使えない。**

| 目的 | 使うコマンド |
| --- | --- |
| ボトルネックを探す | `measure/run-measure.sh` |
| スコアを測る | `static-proxy/run-bench.sh` |

## 4. レポートの読み方

**`pt-query-digest`** は `# Profile` の表を見る。`Response time` はそのクエリ形に費やした合計時間。1回が速くても回数が多ければ上位に来る。`Calls` が回数、`R/Call` が1回あたりの秒数。

個別のクエリは `# Query 1` 以降に詳細が出る。ここで見るべきは `Rows examine`(読んだ行数)と `Rows sent`(返した行数)の比。**1行返すために何千行も読んでいたら、インデックスが無い証拠。**

**`alp`** は `SUM` の降順で並べている。`SUM` はそのエンドポイントに費やした合計応答時間。`AVG` が小さくても `COUNT` が多ければ `SUM` は大きくなる。改善の優先度は `AVG` ではなく `SUM` で判断する。

## 5. ベースライン計測(2026-10-02)

無改造の状態で 20 秒走行した結果。

### MySQL: 合計実行時間の上位

| 順位 | クエリ | 回数 | 合計秒 | 割合 |
| --- | --- | --- | --- | --- |
| 1 | `COMMIT` | 24,882 | 31.70 | 20.8% |
| 2 | `SELECT status FROM ride_statuses WHERE ride_id = ? ORDER BY created_at DESC LIMIT 1` | 25,168 | 31.21 | 20.5% |
| 3 | `SELECT * FROM ride_statuses WHERE ride_id = ? AND app_sent_at IS NULL ORDER BY created_at ASC LIMIT 1` | 10,504 | 15.08 | 9.9% |
| 4 | `SELECT * FROM ride_statuses WHERE ride_id = ? AND chair_sent_at IS NULL ORDER BY created_at ASC LIMIT 1` | 8,849 | 13.37 | 8.8% |
| 5 | `SELECT * FROM ride_statuses WHERE ride_id = ? ORDER BY created_at` | 7,929 | 11.51 | 7.6% |
| 6 | `ownerGetChairs` の走行距離集計(ウィンドウ関数) | 55 | 8.04 | 5.3% |
| 7 | `ADMIN PREPARE` | 156,082 | 7.44 | 4.9% |

### nginx: 合計応答時間の上位

| エンドポイント | 回数 | 平均秒 | 合計秒 |
| --- | --- | --- | --- |
| `GET /api/app/notification` | 10,508 | 0.016 | 171.86 |
| `GET /api/chair/notification` | 13,355 | 0.010 | 139.70 |
| `POST /api/chair/coordinate` | 5,256 | 0.020 | 106.94 |
| `GET /api/app/nearby-chairs` | 64 | 0.156 | 9.97 |
| `GET /api/owner/chairs` | 56 | 0.149 | 8.36 |

### ここから分かったこと

**ride_statuses にインデックスが無い。** 2〜5 位はすべて `WHERE ride_id = ?` で 1 行だけ欲しいクエリなのに、`Rows examine` は平均 4,580 行だった。つまり毎回テーブル全件を走査している。この 4 本で合計 52,450 回、約 71 秒。**DB 時間のおよそ半分がここ。**

**`chairs.access_token` にもインデックスが無い。** 椅子の認証でも同じことが起きている。

**毎回クエリを準備し直している。** `ADMIN PREPARE` が 156,082 回。クエリ1本ごとに「準備 → 実行 → 破棄」で MySQL と 3 往復している。

**COMMIT が 1 位。** 1回 1.3ms。`innodb_flush_log_at_trx_commit = 1` と `sync_binlog = 1` でディスク書き込みの確定を待っているため。アプリを変えずに削れる。

**通知のポーリングが回数で支配している。** 上位 3 つのエンドポイントで全体の大半を占める。1回あたりは速いので、まず回数の多い経路を安くするのが効く。

**静的ファイルのクライアントキャッシュは既に効いている。** 静的ファイルへの 5,056 リクエストのうち 3,629 件(72%)が 304 で返っていた。nginx の ETag が自動で働いている。`Cache-Control: immutable` を足せば残りも減らせるが、伸びしろは小さい。

## 6. スコア推移

スコアは `static-proxy/run-bench.sh` で 60 秒走行して測る。環境の揺れがあるため、同じ条件で測り直して比較する。

| 日付 | 変更内容 | スコア | 備考 |
| --- | --- | --- | --- |
| 2026-10-02 | 無改造(初回計測) | 7,993 | アクセスログ出力を入れる前 |
| 2026-10-06 | 無改造(ベースライン) | 8,337 | アクセスログ出力あり。以降はこれと比較する |
| 2026-10-06 | インデックス8本を追加 | **9,007** | +8.0%、エラーゼロ |

7,993 と 8,337 はどちらも無改造だが、計測環境のアクセスログ出力の有無が違うため直接は比較できない。
インデックスの効果は、条件を揃えた 8,337 → 9,007 で見る。

## 7. インデックス追加後の計測(2026-10-02)

60 秒走行。インデックスは効いたが、**ボトルネックの顔ぶれが入れ替わった。**

| 順位 | クエリ | 回数 | 合計秒 | 割合 |
| --- | --- | --- | --- | --- |
| 1 | `COMMIT` | 87,810 | 107.66 | 56.1% |
| 2 | `ownerGetChairs` の走行距離集計(ウィンドウ関数) | 166 | 25.49 | 13.3% |
| 3 | `ADMIN PREPARE` | 535,332 | 19.11 | 10.0% |
| 4 | `SELECT status FROM ride_statuses WHERE ride_id = ? ...` | 91,082 | 5.38 | 2.8% |

`ride_statuses` の最新ステータス取得は 2 位から 4 位に下がった。

| | 1回あたり | 読んだ行数 |
| --- | --- | --- |
| インデックス前 | 1,240 µs | 4,580 行 |
| インデックス後 | 59 µs | 1 行 |

**21 倍速くなり、しかも 3.6 倍の回数をさばいた。** 全体の `Rows examine` も 183 万クエリに対して 103 万行(平均 0.59 行)まで落ちた。

### スコアの伸びが +8% にとどまった理由

DB は劇的に速くなったが、スコアはそれほど伸びなかった。ベンチマーカーのログに答えがある。

```
92.5%のライドは椅子がマッチされるまでの時間に不満がありました
```

**スコアを決めているのは DB の速さではなく、マッチングの待ち時間。** `internalGetMatching` は 0.5 秒ごとに呼ばれて 1 件だけマッチさせる実装なので、どれだけ DB を速くしても 1 秒に 2 件しかマッチしない。ここが天井になっている。

「DB の実行時間の内訳」と「スコアを決めている要因」は別物、という教訓。
